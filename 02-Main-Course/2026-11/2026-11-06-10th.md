## 1. 채팅 메시지와 소켓 연결

### 1-1. 시스템 메시지도 채팅으로 취급한다

오늘 새롭게 알게 된 점은 **시스템 메시지도 채팅 메시지로 취급할 수 있다는 것**임.

기존에는 사용자가 직접 입력한 텍스트, 사진, 동영상 등을 채팅이라고 생각했음. 하지만 카카오톡에서 누군가 대화방을 나갔다는 안내나 '여기까지 읽었습니다'와 같은 표시도 대화 흐름을 구성하는 메시지로 다룰 수 있다는 것을 알게 됨.

| 종류 | 예시 |
| --- | --- |
| 텍스트 메시지 | 사용자가 입력한 내용 |
| 미디어 메시지 | 사진, 동영상, 파일 |
| 시스템 메시지 | 사용자 입장 및 퇴장 안내 |
| 읽음 관련 표시 | '여기까지 읽었습니다' |

메시지마다 화면에 표시되는 방식은 다르지만, 대화의 흐름 안에서 각각의 역할을 가짐. 또한 수업에서는 채팅 메시지를 같은 라인에 겹쳐 놓지 않고 별도의 줄로 배치한다는 점도 배웠음.

평소 별다른 생각 없이 사용하던 채팅 화면도 실제로 구현하려면 메시지 종류와 배치 방식을 고려해야 한다는 점이 흥미로웠음.

### 1-2. 소켓 연결로 접속 상태를 파악한다

**소켓(Socket)**은 클라이언트와 서버가 데이터를 주고받기 위한 통신 연결의 끝점임. 실시간 채팅에서는 소켓 연결 상태를 통해 사용자의 접속 여부를 파악하는 데 활용할 수 있음.

```text
채팅 리스트에서 대화방 클릭
        ↓
실시간 통신을 위한 소켓 연결
        ↓
메시지 송수신
        ↓
창 닫기·컴퓨터 종료·네트워크 문제 등
        ↓
소켓 연결 종료 감지
```

다만 **소켓 연결이 끊어졌다는 사실이 곧 사용자가 '대화방 나가기'를 눌렀다는 뜻은 아님.** 네트워크 문제로도 연결이 끊길 수 있기 때문임.

기존에는 대화방 입장과 퇴장을 단순한 화면 이동으로 생각했지만, 실제 서비스에서는 서버와의 연결 상태도 함께 고려해야 한다는 것을 알게 됨.

## 2. 로그인 후 이전 페이지로 복귀하는 기능

어제는 Next.js의 로그인과 회원가입 과정을 배웠다면, 오늘은 로그인하지 않은 사용자가 좋아요나 댓글 등의 기능을 이용하려고 할 때 어떻게 처리하는지 알아봄.

예를 들어 비로그인 상태에서 좋아요를 누르면 로그인 안내창이 나타남. 이때 로그인 후 무조건 메인 페이지로 이동한다면 사용자가 방금 보고 있던 게시글을 다시 찾아야 함.

이를 해결하기 위해 **`returnTo` 쿠키**를 사용함.

### 2-1. `returnTo` 쿠키의 역할

```text
비로그인 상태에서 좋아요 클릭
        ↓
로그인 안내창 표시
        ↓
현재 주소를 returnTo 쿠키에 저장
        ↓
/login으로 이동
        ↓
로그인 성공
        ↓
/auth/continue
        ↓
저장된 주소로 복귀
```

오늘 코드에서는 `returnTo` 쿠키에 `httpOnly`와 `sameSite: "lax"` 등의 옵션을 적용함. `httpOnly` 쿠키는 브라우저 JavaScript의 `document.cookie`로 직접 읽을 수 없음.

또한 안전하지 않은 복귀 경로는 기본 경로(`/`)로 바꾸고, 복귀가 끝나면 쿠키를 삭제하도록 구성되어 있었음.

단순히 로그인에 성공시키는 것뿐 아니라 **사용자가 원래 하려던 작업을 이어갈 수 있게 만드는 것**도 중요한 기능이라는 점을 알게 됨.

## 3. 게시글 검색과 GET 요청

게시글 검색에서는 사용자가 입력한 키워드를 서버에 전달하고, 조건에 맞는 게시글을 조회하는 과정을 살펴봄.

### 3-1. GET 방식으로 검색어 전달하기

검색 폼의 이동 경로는 `/posts`이며, HTML 폼에 `method`를 따로 지정하지 않았기 때문에 기본값인 GET 방식으로 제출됨.

```text
/posts?q=검색어&sort=desc
```

| 파라미터 | 의미 |
| --- | --- |
| `q` | 검색 키워드 |
| `sort` | 정렬 방식 |
| `page` | 페이지 번호 |

서버에서는 `searchParams`를 통해 검색 조건을 읽음. 검색어의 앞뒤 공백을 제거하고 연속된 공백을 하나로 정리한 뒤 검색에 사용함.

오늘 코드의 검색 대상은 **작성자 이름(`authorName`)과 게시글 본문(`body`)**이며, 대소문자를 구분하지 않음. 댓글 본문은 검색하지 않음.

### 3-2. 검색 결과와 캐시

```tsx
getCachedPosts(pageNumber, sortOrder, keyword)
```

이 함수는 페이지 번호, 정렬 순서, 검색 키워드를 인자로 받음. 따라서 검색 조건이 다르면 서로 다른 캐시 항목으로 처리할 수 있음.

- `use cache`: 함수의 결과를 캐시함.
- `cacheTag("posts")`: 게시글 목록 캐시에 태그를 지정함.
- `cacheLife("max")`: 캐시 수명 정책을 설정함.

검색 결과를 표시하는 것뿐 아니라 페이지를 이동하거나 정렬 방식을 바꿔도 검색 조건이 유지되도록 구성되어 있었음.

## 4. SSE를 이용한 실시간 알림

오늘 학습한 내용 중 특히 흥미로웠던 부분은 **실시간 알림 기능**임.

다른 사람이 내 글에 좋아요를 누르거나 댓글을 작성했을 때, 새로고침 없이 알림을 표시하려면 서버에서 발생한 변경을 브라우저에 전달해야 함.

오늘 코드에서는 **SSE(Server-Sent Events)**와 **MongoDB Change Stream**을 사용함.

### 4-1. SSE란?

SSE는 서버가 브라우저에 이벤트를 지속적으로 전달하는 기술임. 브라우저에서는 `EventSource`를 이용해 연결함.

```tsx
const eventSource = new EventSource(
  "/api/notifications/stream"
);
```

SSE는 서버에서 클라이언트로 이벤트를 보내는 **단방향 통신**임. 반면 WebSocket은 연결된 양쪽에서 메시지를 주고받는 **양방향 통신**에 사용할 수 있음.

따라서 오늘 메모에 나온 채팅의 소켓 연결과 실제 강의 코드의 SSE 알림은 구분해서 이해해야 함.

### 4-2. 알림이 발생하는 과정

```text
다른 사용자가 내 글에 좋아요 클릭
        ↓
서버에서 좋아요 처리
        ↓
MongoDB에 Notification 데이터 생성
        ↓
MongoDB Change Stream이 변경 감지
        ↓
SSE로 해당 사용자에게 이벤트 전달
        ↓
알림 목록·배지 갱신 및 토스트 표시
```

자신의 글에 직접 좋아요를 누르거나 댓글을 작성한 경우에는 알림을 생성하지 않음. 좋아요를 취소하면 관련 알림도 삭제함.

### 4-3. 주기적 조회 방식과의 차이

일정 시간마다 서버에 새 알림이 있는지 요청하는 방식을 **폴링(Polling)**이라고 함.

하지만 오늘 코드에서는 알림 목록을 5초마다 다시 조회하지 않음. **처음 화면을 그릴 때 알림 목록을 조회하고, 이후 변경 사항은 SSE로 전달받는 방식**임.

구현된 알림 기능은 다음과 같음.

- 로그인한 사용자에게만 알림을 전달함.
- 알림 목록은 최신순으로 최대 20개 표시함.
- 처음 보는 읽지 않은 알림은 토스트로 표시함.
- 토스트는 최대 3개이며, 일정 시간이 지나면 사라짐.
- 알림을 클릭하면 읽음 처리 후 게시글로 이동함.
- '모두 읽음' 기능으로 읽지 않은 알림을 한 번에 처리함.
- 브라우저 탭이 보일 때 SSE를 연결하고, 숨겨지면 연결을 닫음.

평소 흔히 사용하는 알림 기능도 데이터베이스 변경 감지, 서버 이벤트 전달, 브라우저 화면 업데이트가 연결되어 동작한다는 것을 알게 됨.

## 5. Tailwind CSS로 댓글 목록 열고 닫기

기존에는 버튼을 눌러 화면을 바꾸려면 React의 `useState`가 필요하다고 생각했음. 하지만 오늘 코드에서는 **HTML 체크박스와 Tailwind CSS만으로 댓글 목록을 열고 닫는 기능**을 구현함.

### 5-1. 체크박스를 이용한 토글

```tsx
<div className="group/comments">
  <input
    id={`comments-${post.id}`}
    type="checkbox"
    defaultChecked={full}
    className="comments-toggle sr-only"
  />

  <PostCommentCount
    count={post.commentCount}
    htmlFor={`comments-${post.id}`}
  />

  <div className="hidden group-has-[.comments-toggle:checked]/comments:flex">
    {/* 댓글 목록과 입력 영역 */}
  </div>
</div>
```

체크박스에는 `sr-only`가 적용되어 화면에는 보이지 않지만, 라벨을 클릭하면 체크 상태가 바뀜. `htmlFor`와 체크박스의 `id`가 연결되어 있기 때문임.

### 5-2. `group-has`의 역할

```text
group-has-[.comments-toggle:checked]/comments:flex
```

- `group/comments`: 댓글 영역을 하나의 그룹으로 지정함.
- `.comments-toggle:checked`: 체크박스가 선택되었는지 확인함.
- `group-has`: 그룹 안의 자손 요소 상태에 따라 스타일을 적용함.
- `flex`: 조건이 맞으면 댓글 목록을 표시함.

체크박스가 해제되면 `flex` 조건이 사라지고, 기본 `hidden` 스타일에 따라 댓글 목록이 다시 숨겨짐.

`defaultChecked={full}`을 통해 상세 화면에서는 댓글이 처음부터 열린 상태로, 게시글 목록에서는 닫힌 상태로 시작하도록 구성함.

모든 화면 변화에 React 상태 관리가 필요한 것은 아니며, 단순한 표시 전환은 HTML과 CSS만으로도 처리할 수 있다는 점이 인상적이었음.

## 6. 기능에 따라 달라지는 서버 통신 방식

카카오톡과 같은 메신저 서비스가 생각보다 많은 API와 통신 기능을 사용한다는 점도 새롭게 알게 됨.

평소에는 로그인하고, 대화방에 들어가고, 메시지를 보내는 일이 자연스럽게 이어지지만 개발자의 관점에서는 서로 다른 기능을 처리해야 함.

오늘 살펴본 Next.js 코드에서도 기능에 따라 방식이 달랐음.

| 기능 | 사용한 방식 |
| --- | --- |
| 게시글 검색 | HTML 폼의 GET 요청 |
| 로그인 복귀 경로 저장 | Server Action과 쿠키 |
| 좋아요 및 댓글 등록 | Server Action |
| 실시간 알림 수신 | SSE와 EventSource |
| 알림 데이터 변경 감지 | MongoDB Change Stream |
| 댓글 목록 열기·닫기 | HTML 체크박스와 CSS |

또한 `async` 함수, 서버 액션, 클라이언트 컴포넌트는 각각 실행되는 환경과 시점이 다름. 코드를 볼 때 **어떤 기능인지뿐 아니라 어디에서, 언제 실행되는지**도 함께 파악해야 한다는 점을 알게 됨.

## 오늘 새롭게 알게 된 용어

| 용어 | 의미 |
| --- | --- |
| Socket | 클라이언트와 서버가 데이터를 주고받는 통신 연결의 끝점 |
| SSE | 서버에서 브라우저로 이벤트를 지속적으로 전달하는 기술 |
| EventSource | 브라우저에서 SSE 연결을 만들고 이벤트를 받는 API |
| Change Stream | MongoDB 데이터 변경 사항을 감지하는 기능 |
| Polling | 일정 간격으로 서버에 데이터를 요청하는 방식 |
| `returnTo` | 로그인 후 복귀할 페이지 경로를 저장하는 쿠키 이름 |
| `searchParams` | URL의 검색 조건 등을 담은 쿼리 파라미터 |
| `:has()` | 자손 요소 상태에 따라 CSS 스타일을 적용하는 선택자 |
| `:checked` | 체크박스 등이 선택된 상태를 나타내는 선택자 |

## 오늘 느낀 점

오늘은 웹 서비스의 다양한 기능이 실제로 어떤 방식으로 연결되어 동작하는지 조금 더 구체적으로 이해할 수 있었음.

특히 시스템 메시지도 채팅 메시지의 한 종류로 다룰 수 있다는 점이 새로웠음. 사진이나 동영상도 채팅이라는 것은 자연스럽게 생각했지만, 누군가 대화방을 나갔다는 안내나 읽음 관련 표시까지 메시지의 범주에서 생각할 수 있다는 것은 처음 알게 됨.

또한 채팅 리스트에서 대화방을 클릭하는 행동이 단순한 화면 이동이 아니라 실시간 통신 연결과도 관련될 수 있다는 점이 흥미로웠음. 평소 자주 사용하는 카카오톡도 내부에서는 여러 기능과 API가 연결되어 있다는 것을 다시 생각하게 됨.

어제까지는 로그인과 회원가입 자체가 어떻게 이루어지는지에 집중했다면, 오늘은 로그인 이후 사용자의 행동을 처리하고 서버에서 발생한 변화를 화면에 반영하는 방법을 배움.

특히 SSE를 이용한 실시간 알림과 Tailwind CSS를 이용한 댓글 목록 토글을 통해, 비슷하게 화면을 변경하는 기능이라도 목적에 따라 구현 방식이 달라진다는 점을 알게 됨.

아직 각 기술을 어떤 상황에서 선택해야 하는지 완전히 익숙하지는 않지만, 웹 서비스를 구성하는 기능들을 하나씩 연결해서 이해해 가고 있음.
